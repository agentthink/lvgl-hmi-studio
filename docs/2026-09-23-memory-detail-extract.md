### 14.1 三条新纪律（笔记 §4.1 那一行的全文）

#### ① 负控「没有测试匹配」与「测试通过」在退出码上分不出

**症状**：生产负控 p1 的 filter 打在一个 `App.UiTests` 的类上，却跑在 `Core.Tests` 上
⇒ `dotnet test` 打印「没有测试匹配」并**返回 0** ⇒ 脚本把它记成 `OK`（**假绿**）。

**判据**：负控脚本必须带 `no_match()` 守卫 —— 解析输出里的「已通过! - 失败: 0, 通过: N」
那一行，`N == 0` 就报「**这个负控无效**」并让整个脚本非零退出。**「没有测试跑」不是「测试通过」**。

**同族**（同一次会话踩到）：判据自己也要**自带信息** —— xunit 会**截断**长断言消息，
所以「红」要 `Assert.True(count == 0, 拼全文)` 而不是让框架帮你说。

#### ② 三态闭包里「工厂构造」与「真实产出」必须分维

**症状**：`RecipeCloneIssueCodes.REJECTED` 由 `RecipeCloneResult.Failed(...)` 这个**工厂**
造得出来，但产线上**不可确定性复现**（`Recipe.Id = Guid[..8]`，撞车是概率事件）。
判据的 `NotProducible` 表把它记成「产不出」，而「工厂能造」又被闭包的 produced 集合收走
⇒ **`NotProducible ∩ produced ≠ ∅`** ⇒ 判据**自红**。

**修法**：给命中加一维 `Hit.ReachedByProducer`，闭包只问 `ReachedByProducer == true` 的那些；
并断言 `produced.Count >= 1`（否则分维之后闭包可以**空着绿**）。

**同时**：`NotProducible` 需要**担保方判据**（登记 #49：担保方自己不能是死的）——
本项钉住的是「工厂确实挂在产出方的失败分支上」四件事：

1. `CloneRecipe` 的签名是 `RecipeCloneResult`（不再是 `public Recipe` 声明非空）；
2. 源码里**没有** `return null!`；
3. `AddRecipe(clone)` 的出现次数 **==** `if (!AddRecipe(clone))` 的出现次数
   （守卫 `bool` 不许被丢）；
4. 两个工厂各**恰好 1 处**构造。

**推广**：任何「概率性失败码」（哈希前缀撞车、随机端口占用、时序窗口）都属本档 ——
**工厂造得出 ≠ 产出方会发**。

**症状**：`TryRebuildPanels(rebuild, onError)` 的 helper 行为测试**全绿**，而

`RebuildAllPanels()`）—— 用户面对的仍然是「异常被吞」。

**修法**：**两条一起发**，缺一不可：

- **行为判据**：喂一个会抛的委托，断言返回 `false` 且 `onError` 收到的串是渲染后的失败文案；

⚠ 切片段时**needle 要写实际出现的形状** —— 我第一版 needle 写 `RebuildAllPanels();`
（带分号）而源码里是 lambda 里的 `RebuildAllPanels()`，判据假红。

### 25.2 🩸 读数不许有两义：新分量第一次出现「有 ↔ 没有」时就定**三档**

阶段 111 首跑 7 条红 1 条，点名 `BtnAddSlave：**未声明**的分量「从站启用」从 0 变成了 1`
（新子设备默认 `IsEnabled = true`）。**判据按设计工作**，但成因那侧才是收获：
`SlaveEnabled` 当时写的是两档 ⇒ **`0` 同时意味着「没有子设备」与「子设备被停用」**。

### 25.4 🩸 对拍两次门禁：先**归一 ＋ 排序**，再谈差异

同一套代码跑两次 `ci-gate.sh`，逐行 diff 会出现一堆差异，**全不是内容差异**：

| 差异 | 真因 |
|---|---|
| 构建行（`X -> …/bin/Release/…dll`）顺序不同 | MSBuild **并行**构建 ⇒ 完成顺序不稳定 |
| 用例项目的运行顺序不同 | `dotnet test` 多工程**并行** ⇒ 报告顺序不稳定 |
| `数据收集器"Blame"消息:` 挂在不同的工程下 | 同上（同一批行换个归属） |
| `持续时间: 990 ms` vs `持续时间: 1 s` | 归一正则只吃了 `[0-9]+ s` ⇒ **毫秒档漏网** |
| 日志行数差 1 | `GATE_EXIT=0` 打在**日志内**还是**日志外**（取决于怎么重定向） |

⇒ 做法：`归一（墙钟 / 持续时间(ms\|s) / 绝对路径）→ 剔掉 Blame 行 → sort → diff`，
拿**排序后的多重集**相等当作「无内容差异」。阶段 111 实测：**838 行 vs 838 行，完全一致**。
⚠ 行数**不能**当内容指标（它取决于重定向方式）。

### 25.7 🩸 「退出码没落日志」与「报一致要报口径」（阶段 111 回填时新得，两条都是踩出来的）

**一、`GATE_EXIT` 没进日志 ⇒ 那一跑不可复算**（本项目**第 4 次**踩）

阶段 111 的 `gate1` / `gate3` 两跑，日志末行都是 `🎉 门禁全部通过（7 步）`、正文 0 警告 0 错误，

```bash

# ✅ 整条（含重定向与 echo）都在 bash -c 里
bash -c 'cd <repo> && bash scripts/ci-gate.sh > .workbuddy/tmp/sNN-gateK.log 2>&1; echo "GATE_EXIT=$?" >> .workbuddy/tmp/sNN-gateK.log'
```

**唯一症状**：末行没有 `GATE_EXIT=` ⇒ 收口时 `tail -2` 一眼可见。**别靠"我记住了"防它**。

处置**要看树动没动过**（这一条是新的）：

| 情形 | 处置 |
|---|---|
| 那一跑之后**工作树没再变** | **同一条命令另开日志原地复跑**（`…b`），两跑都留档 |
| 那一跑之后**树已经走了**（后面又提交了别的批） | 🩸 **不许**拿新日志冒充那一跑 ⇒ 记「退出码**未留档 / 不可复算**」，改用**包含关系**：后一批的绿是在**包含它的树**上跑的（本项目：`gate2` 覆盖 `gate1` 的改动），并在收口清单里如实登记这个瑕疵 |

**二、报「两次跑一致」必须同时报口径**

同一阶段里，我先后用**两套归一**量了同一对日志，得到**两个数**：

### 27.1 🩸 序数也要现场数（「合计要相加核对」的同一族）

**事实**：阶段 111 的**专题标题**写「第五层的**第七个**宿主：`CommunicationConfigView`」，
而**它自己** §111.8 的结论是「判据的权威行：`宿主 6 个；按钮 91 条…` —— 本轮只新增 1 个宿主
⇒ **本轮之前是 5 个**」。⇒ 那一个是**第六个**；阶段 112 的 `TrendConfigView` 才是第七个。
同一个错序数**传了 4 处**：专题标题、`project-status` §111 标题、登记表 `#39` 单元格、
`2026-09-23-memory-detail-extract.md` §25 标题。

**成因**：与 §111.8 记的「手写**合计**从邻近事实借数字」**同源** —— 这次借数字的是**序数**，
而且正确答案就在同一份文档往下 20 行的地方（不用去找邻近事实）。

**处置按文档性质分叉**：
| 处 | 性质 | 处置 |
|---|---|---|
| 专题标题 / `project-status` §111 标题 / 登记表 `#39` | 活文档 | 就地改 ＋ ⚠ 注 |
| 析出文档 §25 标题 | **已落地快照** | **不手改** ⇒ 在活文档里点名（同 §111.8 对**不可改的提交信息**的处置） |

**规矩（三条，第 2、3 条是新增的）**：
1. **合计要相加核对**（清单是**数**出来的、合计是**抄**来的 ⇒ 合计错了**不红**，§25.3）；
2. **序数要现场数** —— 序数也是手写的事实，同样会借数字；
3. ⚠ **摘要 / 交接笔记里带过来的序数同样不算数**：本轮一开始也把它记成「第八个」，
   是**现数 `Hosts` 逐项清单**（7 项）＋ **运行期表卫生读数**（`宿主 7 个`）才纠正回来的。
⇒ **引用任何计数 / 序数之前，先找一遍它的可数清单或运行期读数。**

### 27.2 🩸 `Inert` 可以是**零信息**的：先补探针、再补订阅

**事实**：`TrendConfigView` 的 6 条 `Inert` 记的是第四种成色「**事件从未订阅**」。
初版宿主注释写「补上订阅之后这 6 条会**当场变红**」—— **这句话不成立**。

**根因**：本层 `Inert` 的口径是「**探针一字不变**」，而当时那 4 个探针读的全是**条数**
（趋势数 / 笔数 / 两个列表长度），而那两个处理器写的是**布尔位**
（`ShowLegend` / `ShowGrid` / `ShowXAxis` / `ShowYAxis` / `ShowPoints` / `IsEnabled`）
⇒「处理器**写了**模型」与「处理器**没接线**」在读数上**完全同形**，判据原理上看不见区别。
＝「**面的边界 ≠ 没有缺口**」：**谓词里没有的东西，面就看不见。**

**处置**：**先补探针、再谈红不红**。顺序反了，补完订阅判据照样绿，人会以为「本层已覆盖」
—— 那是本层最怕的**假闭环**。

**负控钉法**（三支，同时钉住那个顺序）：NC6 给「图例」补订阅 ⇒ 红；
NC7 给「显示点」补订阅 ⇒ 红；NC8 拿新探针做**布景** ⇒ 布景守卫报红。
⚠ 注入**只加订阅、不动探针** ⇒ 能点红**完全是因为 6 个探针已经在位**；
**在量的那一遍之前，同样的注入是绿的。**

**新探针的三条设计决定（可复用）**：
1. 数「**关着的 / 停用的**」而不是「开着的」⇒ 初值**天然全 0**（与「新建对象」的默认值一致；
   反过来数会让「新建」那个按钮**平白多出四条与它无关**的声明）。
2. **全工程累计**，不是「当前那一个」：私有字段（`_currentTrend` / `_currentPen`）表里够不到，
   且中途会**换人**；累计口径只回答「**有没有任何一条被改过**」。
3. **一条声明都不读** ⇒ 一动就是「**未声明分量外溢**」报红。

### 27.3 🩸 声明顺序可以是判据的一部分（不只为「够得着」）

前几个宿主的顺序是为了**够得着**（前提由上一步点击造成）。这一轮多了一个用途：
**决定那两条 `Inert` 能不能被证伪。**

`OnPenPropertyChanged` 首行是 `if (_suppressPenEvents || _currentPen == null) return;`，
而「装上 `_currentPen`」的**唯一活路**是 `BtnAddPen` ⇒ 那两条 `Inert` 是
「**未接线 ＋ 前提**」的**合取**。

| 排法 | 结果 |
|---|---|
| 排在 `BtnAddPen` **之后**（本轮采用） | 光补订阅就点得红 ⇒ 负控 NC7 成立 |
| 排到**表尾**（`BtnDeletePen` 之后） | `_currentPen` 已被清成 `null` ⇒ 注入照样**绿** ⇒ 退化成零信息 |

⇒ **挪位置会把负控悄默弄失效** ⇒ 表里必须写注释说明这件事。

### 27.4 🩸 改写类脚本的**自检本身**也要能证伪

本阶段连踩两次，**都不是内容错、而是自检错**：
1. 对**非追加**编辑用了 `out.endswith(new)` ⇒ 写完第一处后**中途退出**、第二处没落
   ⇒ 留下**半应用状态**（`#39` 补记进了、`#65` 行没进）；
2. 补偿脚本的断言**期望值写错** ⇒ **假警报**（fail-closed 方向，安全）。

⇒ **规矩**：改写类脚本**要么幂等、要么能明确报告「哪一处落了、哪一处没落」**；
原子性 / 回滚由脚本负责，别指望人从结果里看出来。

**附（同族好用的取证手段）**：`git show HEAD:<文件>` 是「**本轮之前**」的**权威取数面** ——
拿它逐名字核对「顺带覆盖」比推测可靠（本阶段据此核出 `BtnTitleClose` / `ChkShowGrid` 两个，
与「残余应掉 10、实测掉 10」对账闭合）。

### 27.5 🩸「刻意排除」的依据可以随**声明方式**而变

阶段 111 §111.9 把 `TrendConfigView` 列入「带 500 ms 刷新定时器 ⇒ **刻意没进**」。
本阶段解禁的**依据**是：那个定时器的**回调体判 `_isRecording`**，而记录入口**恰恰是我们不点的**
`BtnToggleRecord`（登记 `Never`，理由＝读数会抖）⇒ **不点它就不会 `new DataLogger`、不会写盘**。

⇒ **规矩**：「带定时器 / 真写盘」**不是绝对禁区**；要问的是「**那个入口按钮会不会被点到**」。
排除理由要写成**可复核的条件**，不是「有定时器」这种标签 —— 标签会**挡住**本来能收的面。

## 28 阶段 113 追加（第五层的第八个宿主 ＋ 一次产品修复 ＋ 五条新教训）（2026-09-27 压缩析出）

### 28.1 🩸 名字级残余会**永久豁免**"已经提过名字"的缺口

残余探针按**名字**去重（`guard-residual.py` 的口径 = 守卫源码里含 `"<名字>"` 字面量）。
后果：一个缺口只要被**任何一层**提过一次名字（哪怕登记成「静默」），它在残余里就**再也不出现**。
阶段 113 实测：`UserManagerView` 的 **8 个按钮零接线**，但它们在第三层
`DialogInnerInvocationUiTests` 里被逐个登记成 `Quiet(...)` 过 ⇒ 残余读数里**根本没有它们**，
而残余列出的 9 个名字是**另一族**（权限复选框）。

⇒ **规矩**：名字级口径**只能用来排优先级，不能用来判"这一层覆盖完了"**。
要判"覆盖完了"只能在**运行期面**上判（本层的面守卫：宿主内每个具名 `Button` 都要在表里有桶）。
⚠ 这也是「**面的边界 ≠ 没有缺口**」的第三次形态（前两次见 §27.2 与 §18.2①）。

### 28.2 🩸 量「谁在写」要搜**写入点**，不是搜**公开入口名**

阶段 113 开工前下过一句结论：「用户管理一条审计都不落」，依据是 `RecordAudit(` 全仓只有
`MainWindow` 导出那一站在调。**真跑一次读数直接打脸**：`BtnAddUser` 审计 0→1、
`BtnToggleEnabled` 1→2。
根因：审计条目有**两级入口** —— 公开的 `RecordAudit(...)` 只是给仓外调用方的壳，
`CreateUser` / `DeleteUser` / `SetUserEnabled` / `ChangeUserRole` 走的是**私有**
`AppendAudit(...)`（写同一个 `_auditLog`、同样触发 `AuditLogged`）。

⇒ **规矩**：查"谁在写某个集合"时，搜的是**写入点**（`<集合>.Add` / `<集合>[k]=` / 私有 helper 名），
**不是**公开方法名。公开入口往往只是**其中一个**调用方，而且常常是最少用的那个。
⚠ 这一条与 §26（阶段 111 的「合计从邻近事实借数字」）**同源**：都是**用一个方便查的东西
代替了要查的那个东西**。

### 28.3 🩸 对拍要区分「**重排**」与「**真差异**」

`scripts/ci-gate.sh` 的日志里，MSBuild 的引用清单（`X -> ...dll`）与并行测试程序集的结束顺序
**每次都不同**。逐行 `difflib` 会把「同一行换了位置」报成一对 `+/-`：
阶段 113 实测 —— 与上一阶段 `gate4` 的逐行 diff **46 行位移**，而**真差异只有 2 行**
（`App.UiTests 588 → 589`）。

⇒ **做法**：`gate-diff.py` 改成 ① 先剥墙钟（`已用时间` / `持续时间:` / `总时间` /
`AUDIT <ISO 时间戳>` / 裸时间戳）；② 用 `Counter` 做**多重集差**得真差异；③ 逐行位移**单列一个数**。
否则 `+N / -N` 这个读数会把「本阶段改了什么」直接埋掉 —— 而它正是对拍唯一要回答的问题。

### 28.4 负控还有第三种档：**「必须保持绿」的反证（PC1）**

此前负控只有两种：**注入 ⇒ 必须红**（判据在管）、**正控**（判据不该误报）。
阶段 113 冒出第三种：**注入 ⇒ 必须绿**，用来证的**不是判据、而是对判据机制的一句解释** ——
「这 9 条 `Inert` 变红需要**订阅 ＋ 处理器体**两个条件同时成立」。
没有 PC1，NC6 变红可以有两种解释（订阅够了 / 还不够），**NC6 单独跑分不出来**。

⚠ **但它同时是脆的**：PC1 证明的是「按**现有实现**，只补订阅不改变读数」。
实现一改（例如把那个空壳处理器换成行内 lambda），PC1 会失效而**没有任何东西会告诉你**。
⇒ 这一档要当成「**对实现的注解**」登记，别当成判据：实现变了要**手工复核**它。

### 28.5 🩸 门禁日志必须**自足**：退出码要落进日志本体

阶段 113 第一次跑门禁时写成 `... > log 2>&1; echo GATE_EXIT=$?` —— 退出码只到了**终端**，
**没进日志**。后果：那份日志**不能当"绿"的证据**（阶段 112 起日志末行本该是 `GATE_EXIT=0`）⇒
该次读数**作废重跑**，并把 `s113-gate.sh`（`echo "GATE_EXIT=$?" >> "$LOG"`）固化下来。

⇒ **规矩**：跑门禁一律用**带退出码落盘**的马甲脚本；引用任何"绿"之前，
**先看日志末行有没有 `GATE_EXIT=0`**。这与「先核时序再引用证据」是同一条纪律的两半：
时序管「读数晚于改动」，退出码管「这份日志自己说清了它跑成什么」。

## 29 阶段 114 追加（收口登记 `#65`：补回 10 处订阅 ＋ 四条新教训）（2026-09-27 压缩析出）

阶段 114 把登记 `#65`（`TrendConfigView` 的订阅缺失）**从「6 个控件 / 4 处订阅」改大为
「6 条处理器 × 10 个控件」并收口**，过程中**补订阅这个动作自己撞出一条产品回归**。
专题 ⇒ `docs/2026-09-27-trend-config-event-wiring.md`；状态表 ⇒ `project-status.md` §114。

### 29.1 🩸 接线补齐 ≠ 无害：反向同步必须抑噪（「自我巩固锁死」）

**形状**（本阶段实测，非推理）：一个控件**双向**（`IsCheckedChanged` → 处理器写模型），
而「模型 → 控件」的反向同步（`UpdateTrendDisplay()`）**一枚一枚**写那一族控件，
处理器却**一次读全部**。补上订阅之后：

1. 写到某一枚 ⇒ 触发处理器 ⇒ 处理器把「**控件当时的残值**」当成用户意图写回模型；
2. 随后那几枚又从**已被写坏**的模型刷回来 ⇒ 值不再变化 ⇒ **不再触发**（自我巩固）
   ⇒ 错误被**静默锁死**，界面上一点异常都看不出来。

**两处现场**（`.workbuddy/tmp/s114-post.log`）：

- **初态**（构造函数里那一遍 `UpdateTrendDisplay()` 就够了）⇒ 第一条趋势的
  「网格 / X 轴 / Y 轴」被写成**关**（三个分量 0 → 1）—— **打开这个对话框本身**就改了用户数据；
- `BtnAddTrend` ⇒ 新趋势的「X 轴 / Y 轴」被写成关（`关X轴趋势` / `关Y轴趋势` 1 → 2）。

⚠ **被写坏的是「哪几位」取决于控制件残值**（＝上一条趋势的值 + XAML 初值 `null`），
**形状不固定** ⇒ 只能由守卫兜住，不能靠人肉 review。

**修法：照作者自己已有的模式补** —— `UpdatePenEditor()` 早就有 `_suppressPenEvents`
（连 `PenColorCombo.SelectedIndex` 那行都在窗口内），`UpdateTrendDisplay()` 漏了同款
`_suppressDisplayEvents`（字段 ＋ 两行赋值 ＋ 处理器首行 `||`）。
复跑 `s114-post3.log`：**9/9 通过**，初态四个显示位全 0。

⇒ **这是第五层（动作面）的第二种用途**：它不只记「接线缺不缺」，还拦
「**接线补上之后会不会把别的写坏**」。前七个宿主从没触发过这一档 —— 因为它们的接线一直是全的。

⚠ **同形未发也值得记**：`OnTimeWindowChanged` 是六条处理器里**唯一没有抑噪守卫**的，
且它的程序性写入点（`UpdateTrendDisplay()` 里 `TimeWindowCombo.SelectedIndex = i`）落在
抑噪窗口**之外**。今天无害（循环只在匹配到选项时才赋值 ⇒ 写回的是同一个值），
**但形状一模一样** ⇒ 已开登记 `#67`。

### 29.2 🩸 负控两种红的形状：非末位落「后一枚」、末位走**空声明自检**

同一处理器管**多枚**控件时，摘掉其中一枚的订阅，红的形状**取决于它在族里的位置**（实测 8 支负控）：

| 位置 | 红的形状 | 点名在哪 |
|---|---|---|
| **非末位** | 「**未声明**的分量外溢」 | **后一枚**那一步（后一枚触发处理器时，把前一枚的**陈旧控件值**一起写进模型） |
| **末位** | 「声明成 `Moves`，但**声明的分量一个都没动** ⇒ 这条声明等于没写」 | **自己** |

⇒ **归因到的是「检测点」，不是「动手点」**：照日志直接归因（「NC10 摘的是图例 ⇒ 红在
`ChkShowGrid` ⇒ 说明 `ChkShowGrid` 有问题」）**会归错**。
⇒ 两档合起来才完整：**非末位靠外溢、末位靠空声明自检**；缺任何一档，族里就会有一枚
**摘了订阅也无人过问**。

### 29.3 🩸 登记项的盲区 ＝ 面的盲区（清点要按**处理器**）

登记 `#65` 写「6 个控件」「补 4 处订阅」—— 实测 **6 条处理器 × 10 个控件**。
漏掉的两条是 **`OnPenColorChanged`@`PenColorCombo`** 与 **`OnTimeWindowChanged`@`TimeWindowCombo`**
（两个 `ComboBox`），它们**上一轮看不见** —— 因为登记表与第五层的面**都只看 `Button` 族**。

⇒ 这比「面的边界 ≠ 没有缺口」更难受的一档：**盲区经手写进了账本**，下一轮照账本读
就永远读不到它。**处置**：清点缺口按**处理器**为单位（N 条处理器各自找挂点），
**不按「面上看得见的控件」**；登记一个「整族接线缺失」的项时，先把该族的**全部**挂点列出来，
再标哪些在面内。

### 29.4 名字级口径第三例：**修好也不动**

本阶段补了 10 处订阅、修掉一条真回归，残余面读数 **65 格 / 57 名字 / 21 视图 —— 一字不变**
（覆盖仍 187 / 244 ＝ 76.6%）。**原因不是漏记**：残余是**名字级**口径，而该视图 12 个名字
早在阶段 112 建宿主时就全部进了判据文件 ⇒ **它从来不在残余里**。

🩸 「**提过名字就永久豁免**」至此**三例齐全**：

| 例 | 现象 | 后果 |
|---|---|---|
| 阶段 109（`SettingsDialog`） | 同名的别视图按钮被顺带计入 | 降幅**高估** |
| 阶段 111（`CommunicationConfigView`） | `BtnTitleClose`（28 个 `.axaml` 里都有）早被别处提过 | 残余**低估** |
| 阶段 114（`TrendConfigView`） | 该视图名字全在判据文件里 | 修好也**完全无反应** |

⇒ **名字级口径只能排优先级、不能判「覆盖完了」**；要量「本阶段真收了多少」，
必须对**两份日志逐视图求差**，或直接数「运行期真覆盖的控件数」。

### 29.5 从 §4.1「换宿主」那条析出的细节（原文保留）

- 🩸 **换宿主＝换数据面形状、不换骨架**；**两段式写入**（只标脏逐条 `Inert` ＋ 落盘那条 `Moves`
  一次见证 N 个分量，**负控两半各一支**）；**`Inert` 要写成色**；
- 🩸 **`Inert` 可能零信息**（探针读不到处理器写的字段 ⇒「接线了」与「没接线」**读数同形**

修法是**就地读**。判据最初只有两条「不许有」：
① `EvaluateCondition` 的形参表不得出现 `Dictionary<string, double>`；
② `EvaluateAll` 的方法体不得出现 `_lastVariableValues`。
—— 这两条**最省事的「改法」是把就地读删掉**：引擎根本不再读值 ⇒ **① ② 反而更绿**。
⇒ 必须补第三条**反向腿**：③ `EvaluateCondition` 的方法体**必须**出现 `_lastVariableValues`。

**为什么不是「多加一条保险」**：①②③ 是**同一条契约的两半**（「值只在单配置评估里取」
＝「入口不许取」＋「单配置评估必须取」）。只写一半，判据的**真值集合**与它声称守的集合**不重合**。
这与本仓「**面到 0 ⇒ 改性质**」是**镜像**：那条讲「面看不见缺口」，这条讲「**删了功能也能变绿**」。

**通式**：对每一个「零出现 / 不许有 / 不得」断言，问一句
「**把这东西整个删掉，这条还绿吗？**」绿 ⇒ 缺反向腿。反向腿有三种常见形态：
- **必须在场**：某标识符 / 某 API 必须出现在指定作用域内（本例 ③）；
- **必须被调用**：定义了却没人调的清理 / 校验函数（本仓阶段 45「会话清理必须接进 App 生命周期」）；
- **必须成对**：破坏性断言的对照面（本仓阶段 105：断言「坏包不留痕迹」必须配「好包必须建出目录」）。

**负控的三档写法**（沿用铁律②：须能编译、**读汇总行**）：
- **内嵌负控**：语料喂给**同一个**判定函数（不是另写一份相似逻辑），逐支断言**命中数**与**命中腿**；
- **正控全合成**：再造一份「修好之后」的形状，断言**零违规** ——
  没有它，负控证明的只是「三条腿总会红」（＝死判据）；
- **生产负控**（最强）：把缺陷态**注回真文件**，断言判据红、**逐腿点名**、**其余腿仍绿**
  （其余腿若一起红，说明它们只是「总在红」），还原后核对 `sha256` **与** `git diff` 指纹。

**输入面 = 只有那两个方法，不是整个文件**（铁律③：输入面不得含「定义面」）：
文件里 `UpdateVariableValues(Dictionary<string, double> values)` 是**写入口**、
字段声明 `private readonly Dictionary<string, double> _lastVariableValues = new()` 是**定义面**
—— 拿整个文件当输入面，它们自己就会被判违规。
