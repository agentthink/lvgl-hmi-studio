## 112.1 为什么是它：它是第一个「一个处理器都没被调用」的宿主

前六个宿主有一个共同的降级线：**按钮点下去至少会走进某个处理器**（接错了是另一回事，
但接线存在）。第 111 阶段那个「输入面驱动」的宿主也只是「处理器跑了但提前 `return`」。

`TrendConfigView` 不是。**12 个具名按钮里有 6 个的事件订阅整段缺失。**
三条依据（都核过，不是推测）：

| # | 依据 | 读数 |
|---|---|---|
| ① | XAML 里的事件属性 | 只有两个：`PointerPressed=OnTitleBarPointerPressed`、`Click=OnTitleCloseClicked`。**没有任何** `IsCheckedChanged=` / `SelectionChanged=` |
| ② | code-behind 里的 `+=` | 只有 **5 行**，全是按钮的 `Click`（`BtnAddTrend` / `BtnDeleteTrend` / `BtnAddPen` / `BtnDeletePen` / `BtnToggleRecord`） |
| ③ | 那 6 个处理器在全仓的引用 | 去掉 `bin/obj` 后 `grep -rn` **零命中** |

⚠ 对照组是**同一个模式、别的视图在用**：`ScreenManagerView` 与 `PropertyPanelView` 都写了
`IsCheckedChanged="OnPublicChanged"` 这类事件属性 ⇒ **不是 Avalonia 的写法问题，是这个视图丢了订阅。**

后果（用户可见的真缺陷，本层**不修**，只记事实）：

- ⓐ 4 个显示选项复选框（图例 / 网格 / X 轴 / Y 轴）**拨动之后不写回模型**
  —— `OnDisplayOptionChanged` 一次读这四枚，但没人订阅；
- ⓑ 笔编辑器的「显示点」「启用」两枚同理 —— `OnPenPropertyChanged` 是为它们写的，也没人订阅；
- ⓒ 两个列表（趋势 / 笔）的**鼠标选中也是死的** —— `OnTrendSelectionChanged` /
  `OnPenSelectionChanged` 同样没订阅 ⇒ 用户**切不了趋势、选不了笔**。

⚠ 反方向**是通的**（这正是用户能感知到症状的原因）：`UpdateTrendDisplay()` / `UpdatePenEditor()`
都有「模型 → 控件」的单向同步。拨完「图例」之后任何一次刷新都会把它**弹回**原值。

⇒ 另开登记 **#65**（本阶段只登记，不动手）。

## 112.3 🩸 量的那一遍：原措辞是**过头话** —— 「面看不见缺口」的又一例

初版宿主注释写的是：

> ⚠ 修好之后这 6 条 Inert 会**当场变红**，逼人来改声明。

**这句话不成立。** 量的那一遍（在写负控之前先自己试着把「修好」做出来）发现：
**光补订阅不红。**

根因：原来的 4 个探针读的全是「**条数**」——

| 探针 | 读什么 |
|---|---|
| `趋势数` / `末条趋势笔数` | 模型里趋势 / 笔的**个数** |
| `趋势列表` / `笔列表` | 两个 `ListBox.Items.Count` |

而那两个处理器写的是**布尔位**（`ShowLegend` / `ShowGrid` / `ShowXAxis` / `ShowYAxis` /
`ShowPoints` / `IsEnabled`）⇒ **「处理器写了模型」与「处理器没接线」在读数上完全同形**，
判据原理上看不见区别。

这正是笔记里那条 **「面的边界 ≠ 没有缺口」**：*谓词里没有的东西，面就看不见。*
那 6 条 `Inert` 在补探针之前是**零信息**的 —— 有没有那 6 行注释，判据读数一模一样。

**处置：先补探针、再谈红不红。**顺序反了，补完订阅判据照样绿，人会以为「本层已覆盖」
—— 那是本层最怕的一种**假闭环**。

## 112.4 表（12 条 / Probe **10** 个）

### 六个新探针（本批的核心）

| 探针 | 读法 |
|---|---|
| `关图例趋势` / `关网格趋势` / `关X轴趋势` / `关Y轴趋势` | `TrendsWith(depot, t => !t.ShowLegend)` 等 |
| `开显示点笔` / `停用笔` | `PensWith(depot, p => p.ShowPoints)` / `p => !p.IsEnabled` |

三条设计决定，每条都有理由：

1. **数「关着的 / 停用的」而不是「开着的」** ⇒ 初值天然全是 `0`。
   依据：夹具那条趋势的四个显示位默认全开、两支笔默认启用（`TrendConfig` / `TrendPen` 的
   属性初值），而 `BtnAddTrend` 新建的趋势**同样全开**、`BtnAddPen` 新建的笔**同样启用**。
   反过来数「开着的」会让 `BtnAddTrend` 平白多出四条**与它无关**的声明。
   ⇒ 这不是凑数，是**选口径**。
2. **全工程累计，而不是「当前那条趋势」** ⇒ `_currentTrend` / `_currentPen` 都是私有字段，
   表里够不到；而 `BtnAddTrend` / `BtnDeleteTrend` 中途会把它换人。累计口径对「写的是哪一条」
   不敏感，只回答本层唯一要问的问题：**有没有任何一条被改过**。
3. **六个探针一条声明都不读** ⇒ 只要被改动就是「未声明分量外溢」报红。
   这是把「Inert 记事实」这条机制**接到能看见的位置**上。

### 4 条 `Moves`（全部靠声明顺序串起来）

| 按钮 | 分量（点击后） | 关键点 |
|---|---|---|
| `BtnAddTrend` | 趋势数 2 / 趋势列表 2 / 末条趋势笔数 0 / 笔列表 0 | 后两个 2 → **0**：新趋势是空的，而点击前读的是夹具那条（2 支笔）⇒ 同时见证「最后一条真的换了人」 |
| `BtnAddPen` | 末条趋势笔数 1 / 笔列表 1 | 顺手装上 `_currentPen` —— **本宿主唯一**能装上它的地方 |
| `BtnDeletePen` | 末条趋势笔数 0 / 笔列表 0 | 前提来自 `BtnAddPen`（中间两条 Inert 不接线、动不了 `_currentPen`） |
| `BtnDeleteTrend` | 趋势数 1 / 趋势列表 1 / 末条趋势笔数 **2** / 笔列表 **2** | 四个分量一起动 ⇒ 把「删掉的是新那条、留下的是夹具那条」钉死 |

### 6 条 `Inert`：本层**第四种成色**（事件从未订阅）

| 按钮 | 处理器（存在但没人订阅） |
|---|---|
| `PenShowPointsCheck` / `PenEnabledCheck` | `OnPenPropertyChanged` |
| `ChkShowLegend` / `ChkShowGrid` / `ChkShowXAxis` / `ChkShowYAxis` | `OnDisplayOptionChanged` |

⚠ 粒度是**按钮**不是处理器：一个 `OnDisplayOptionChanged` 管四枚 ⇒ 表里因此是四条 `Inert`，
不是一条「一族」。四枚合起来是**整族失效**，但拆成四条才看得见「哪一枚被接上了」。

### 2 条 `Never`：两种理由

- `BtnToggleRecord` —— **读数会抖**（与 `CommunicationConfigView.BtnTestConnection` 同档，
  但机制不同）：`StartRecording` 会 `new DataLogger`（1000 ms 采样）＋ 构造函数里那个
  500 ms 的 `System.Threading.Timer` 开始真刷图 ⇒ 两路异步，「点完读到的分量属于哪个瞬间」没有因果保证。
  ⚠ 阶段 111 §111.9 曾把本视图列入「带刷新定时器 ⇒ 刻意没进」。本轮解禁的**依据**是：
  那个定时器的回调体判 `_isRecording`，而记录入口恰恰是我们不点的 `BtnToggleRecord`
  ⇒ **不点它就不会 `new DataLogger`、不会写盘**。
- `BtnTitleClose` —— `ChromeWindow` 标题栏关闭按钮，点了会关窗。

## 112.5 「顺序即语义」这一轮的用法变了：**为负控服务**

前六个宿主里，声明顺序是**为了够得着**（前提由上一步点击造成）。
这一轮它多了一个用途：**决定那两条 `Inert` 能不能被证伪。**

`OnPenPropertyChanged` 的第一行是：

```csharp
if (_suppressPenEvents || _currentPen == null) return;
```

⇒ 那两条 `PenShowPointsCheck` / `PenEnabledCheck` 是**「未接线 ＋ 前提」的合取**。
而「装上 `_currentPen`」的唯一活路是 `BtnAddPen`（两条选择处理器都没接线）。

| 排法 | 结果 |
|---|---|
| 排在 `BtnAddPen` **之后**（本轮采用） | 光补订阅就点得红 ⇒ 负控 NC7 成立 |
| 排在表尾（`BtnDeletePen` 之后） | `_currentPen` 已被清成 `null` ⇒ 注入照样**绿** ⇒ 这两条退化成零信息 |

⇒ 顺序在这里不是「顺手的」，是**判据的一部分**。表里为此写了注释，免得后人挪位置时
把负控悄悄弄失效。
