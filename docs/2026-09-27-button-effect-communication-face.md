## 111.1 为什么是它：前六个宿主都「现场现成」，这个不现成

前六个宿主的数据面形状换过三轮（模型集合计数 → 服务对象属性 → 工程模型 ＋ 草稿），
但它们有**同一个共同点**：**按钮点下去要用的现场，夹具里已经躺好了**。

`VariableManagerView.BtnDeleteAlarm` 的前提是「上一步刚加了一条报警并被自动选中」——
那是**上一步点击**造成的。这一层的「点击顺序就是语义」那条设计，正是为这类依赖准备的。

`CommunicationConfigView` 不一样：

| 维度 | 阶段 107～110 六个宿主 | 111 `CommunicationConfigView` |
|---|---|---|
| 处理器的**第一行**在读什么 | 模型 / 选中项（点击造成） | **文本输入框**（`TxtSlaveVarName` / `TxtBatchNamePrefix` / `TxtBatchCount` / `TxtBatchStartAddr`） |
| 输入框谁来填 | — | **没有人** ⇒ 处理器一律走「为空 ⇒ 只写状态栏并 return」 |
| 列表选中项谁来装 | 上一步点击（`SelectListItemByTag` 之类） | 🩸 **选中的是 `ListBox` 的行为、不是按钮的行为** ⇒ 本层够不到 |
| 面 / `CheckBox` | 20 / 7 / 4 / 26 / 19 | **15 / 2** |

⇒ 如果不加机制，这个视图的 15 条里会有 **11 条**只能登记成
「🥱 输入框是空的 ⇒ 提前 return」那种 `Inert`。而那条 `Inert` 记的是**夹具的形状**、
**不是接线** —— 它会绿着，但它对这一层是**零信息**：把 `Click +=` 整行删掉，它也照样绿。

**这正是阶段 50 那句「造状态能力缺失（选中一行 / 填一个输入框再确认）」的近亲**，
只不过 50 阶段说的是「四层判据只能覆盖『不弹』」，本阶段说的是「第五层只能覆盖『不需要输入』」。

### 两条自陈的盲区（本宿主量出来的，不是被证过的）

1. **`TxtConnName.LostFocus → PersistConnectionName` 不在本层的面内。** 它是「失焦回写连接名」

## 111.3 🆕 新机制：布景（`ClickSpec.Arrange` / `Arranged(...)`）

### 形状

```csharp
private sealed record ClickSpec(string Name, Bucket Bucket, (string Label, string Value)[] Expect, string Why)
{
    /// <summary>点击**之前**的布景。⚠ 只许动输入面分量，跑的时候有自检盯着。</summary>
    public Action<HostContext>? Arrange { get; init; }
}

private static ClickSpec Arranged(ClickSpec spec, Action<HostContext> arrange) => spec with { Arrange = arrange };
```

表里读起来是这样（三处用到它，本阶段唯一的三个 `Arranged`）：

```csharp
Arranged(Moves("BtnAddSlaveVar", "…", ("变量","3"), ("从站变量列表","1"), ("从站首变量地址","40007")),
         c =>
         {
             Control<TextBox>(c.Window, "TxtSlaveVarName").Text = "启动指令";
             Control<TextBox>(c.Window, "TxtSlaveVarAddress").Text = "7";
         }),
```

跑的顺序是：`布景 →（Pump）→ before 读数 → Gesture →（Pump）→ after 读数 → Check`。
布景落在 `before` **之前**，所以布景自己造成的变化**不进断言**（它成了新现场的一部分）。
读数里为每一条带布景的声明另起一行，形如 `BtnSaveEditSlaveVar 布景 → 变量选中=1`。

### ⚠ 它同时是一条**新的作弊面**，所以自带守卫

把「点击的效果」搬进布景里预先做掉（比如布景里直接 `Variables.Add(...)`），
**表面上看不出任何异常**：点击那条腿照旧绿，而本层的两个方向都瞎了。
⇒ 判据里加了一条自检，在布景前后各读一次全分量：

```csharp
var touched = spec.Probes.Where(p => before[p.Label] != after[p.Label]).ToArray();
var illegal = touched.Where(p => !p.IsInputFace).Select(p => p.Label).ToArray();
if (illegal.Length > 0) → 红：「布景改动了**输入面以外**的分量：…」
```

### 分量的三档（本阶段新增第三档）

| 档 | 声明方式 | 进断言？ | 布景能改？ |
|---|---|---|---|
| **数据面** | `Num` / `Str` | ✓ 双向 | ❌ **改了红** |
| **Voice** | `Voice` | ✗（只进读数） | ❌ |
| 🆕 **输入面** | `InputNum`（`Probe.IsInputFace`） | ✓ 双向 | ✓ |

本阶段只标了**一个**输入面分量：`变量选中`。理由是它必须被标 ——
`BtnSaveEditSlaveVar` 的前提就是它，而列表选中是 `ListBox` 的行为、本层没有按钮能重新装上它。

「树选中」（同样是选中项）**刻意没标**：本表没有任何一条布景需要动它 ⇒ 它留在严格的一侧，
布景碰它就红。⇒ **输入面不是「凡是选中项都算」，而是「本表确实需要布景动它」**。

### 四条 `Never` 是**三种互不相同**的理由

| 按钮 | 理由档 | 具体 |
|---|---|---|
| `BtnImportSlaveVars` | 平台桩 | `async Task` ＋ `IStorageProvider.OpenFilePickerAsync` ⇒ headless 拿到的是桩 |

| `BtnTitleClose` | 关窗 | `ChromeWindow` 标题栏的关闭按钮 |

`BtnTestConnection` 是**新的一档**：它既不关窗、也不走平台桩。
本层「不判跨层副作用」那条边界**收不住它** —— 它碰的是**插件程序集里的纯校验方法**。
真正的问题在别处：**它的完成时刻不由 `UiTestHost.Pump` 决定** ⇒ 点击后读到的分量属于哪个瞬间
没有保证，而**可复现性**是本层全部断言的前提（一次抖动的读数会污染**下一条**按钮的 `before`）。
⇒ 要收它，得先给本层加一个「等静默（await quiescence）」的原语，**不是改声明**。
另加一条：跑在 UI 线程上的 `async void` 一旦抛，会变成另一起**无法归因**的崩溃。

本表为它新加了一个分量 `批量面板`（读 `Border.IsVisible` 的 开/关）⇒ 它从「看不见的副作用」

## 111.5 🩸 第一次真红：`从站启用` 漏声明 ⇒ 顺带把**两义读数**改成三档

本阶段第一次跑（`s111-run1.log`）**7 条里红 1 条**，点名原文：

```
CommunicationConfigView.BtnAddSlave：**未声明**的分量「从站启用」从 0 变成了 1
—— 要么把它写进本条的声明，要么这个按钮改了不该改的东西（副作用外溢）
```

**这是判据按设计工作**：`BtnAddSlave` 往连接下挂了一条子设备，而**新子设备的默认
`IsEnabled = true`** ⇒ 单看「启用位」这个分量，它从 0 变成了 1。
我漏了它（只声明了 `从站` / `树选中` / `从站首变量地址`）。

**但真正的收获在成因那一侧**：我当时把 `SlaveEnabled` 写成了两档

```csharp
...FirstOrDefault() is { IsEnabled: true } ? 1 : 0     // 0 = 「没有子设备」 或 「子设备被停用」
```

⇒ 这条读数**有两义**。而它恰好是**同一份数据的两件不同的事**（存在性 vs 启用位）被压进了一个 0。

处置：改成**三档**（`-1` = 这一档还不存在），与我在 `FirstSlaveVarAddress` 上同时定的
「`无从站` / `无变量` 刻意分开」是同一条理由：

| 分量 | 两档（旧） | 三档（新） | 代价 |
|---|---|---|---|
| `连接启用` | 0 = 没有连接 或 被停用 | `-1 / 0 / 1` | `BtnAddConnection` 的声明从 `0→1` 改成 `-1→1` |
| `从站启用` | 0 = 没有子设备 或 被停用 | `-1 / 0 / 1` | `BtnAddSlave` ＋ `BtnDeleteSelection` 各多一条声明 |

🩸 **教训**：一个新分量第一次出现「有 ↔ 没有」的迁移时，就该决定它是不是两义的。
把两义读数留在表里，坏处不是**当轮**出错，而是**下一轮**有人把它读成另一个意思
（`连接启用=0` 很可能被读成「没有连接」）。**多付一条声明的钱，比留一个会误导人的读数便宜。**

## 111.8 ⚠ 本轮更正的文档错误：第五层宿主数 **6 → 5**
