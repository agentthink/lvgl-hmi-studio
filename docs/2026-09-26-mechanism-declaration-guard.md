## 106.1 缺口：三条来源，四处漏法里三处静默

一个「可达机制」在这份守卫里要在**三个地方**各写一遍：

| # | 来源 | 住在哪 | 形状 | 阶段 106 之前**谁在盯** |
|---|---|---|---|---|
| ① | **类注释的机制清单** | 类注释的 `<list>` | `///   <item><b>M19</b> 模拟器编译 / 启动失败诊断码（阶段 103…）` | **没有任何东西** |
| ② | **下界表** | `MechanismFaces_AreNonEmpty` 的**局部数组** | `("M19-模拟器编译码", 3)` | 只盯「面 ≥ 下界」 |
| ③ | **取数** | `ReachableKeys()` | `list.Add(("M19-模拟器编译码", …))` | 只被 ② **单向**引用 |

四条可能的漏法，以及它们当时的现象：

| 漏法 | 现象 | 阶段 106 之前 |
|---|---|---|
| 加机制只改 ③ | ② 里没有下界 ⇒ 那条机制**没有下界**，退化成空集也没人管 | **完全静默** |
| 加机制改 ③② 忘 ① | 清单少一条 | **完全静默**（**M19 就是这样**：阶段 103 落后，阶段 104 才手工补） |
| 清单 id 写错 / 写多 | 清单与表对不上 | **完全静默** |
| 加机制改 ③② 忘 ② | 面 0 < 下界 | 已由 `MechanismFaces_AreNonEmpty` 抓到 |

**为什么手工补过的还会再烂**：阶段 104 那两处欠账是**手工**对齐的（改类注释），
而手工动作**没有任何东西会响** —— 正是本项目反复记的那句
「手工汇总会随每轮推进而失真」。补它的是人，守它的也得是判据。

## 106.2 改法

### (1) 下界表提成字段

`MechanismFaces_AreNonEmpty` 里的 `var minimum = new (string Kind, int Min)[] { … }`
是个**局部变量** ⇒ 判据**看不见它**，「清单 ↔ 下界表」这条比对**在同一个类里**也做不到。
改成 `private static readonly (string Kind, int Min)[] LowerBounds`，
**数值与语义一个不动**（只是可见性变了）。

### (2) 新判据 `Mechanisms_AreDeclaredInAllThreePlaces`：五条断言

| # | 断言 | 抓什么 | 为什么非要它 |
|---|---|---|---|
| 1 | **空集守卫** | 三处各 ≥ 20 条 | 任一处取空 ⇒ 下面的差集**恒真**（假门禁的经典形状） |
| 2 | **id 形状自检** | 每条 kind 必须抠得出 `M<数字>-` | 否则 ①↔② 的 id 比对会**静默错位** |
| 3 | **清单重复条目** | 同一条机制写两遍 | `Distinct` 会把重复吃掉、**差集看不出来** ⇒ 只能单列 |
| 4 | ②↔③ 按 **kind** 双向差集 | 「取数造了下界表没有的 kind」 | **这次真正补上的那一半**（此前静默） |
| 5 | ①↔② 按 **id** 双向差集 | 清单少项 / 写多 / id 写错 | M19 漏的正是这一条 |

比对口径：①↔② 按 **id**（清单只写 `M19`，表里写 `M19-模拟器编译码`）；
②↔③ 按 **kind**（判据的 `byKind.TryGetValue` 就靠那个字符串对上）。

### (3) 为什么不让清单自动生成

清单是 XML 文档注释，每条带一段**人话**（阶段 / 码表 / 下界为什么取这个数）——
那部分正是它的价值、生成不出来。所以做法是**用判据夹住集合**，不是消灭重复。

## 106.6 诚实边界

1. 判据读的是**工作树里的本文件源码**（`AppSourceScanner.FindRepoRoot()` ＋ 文件路径）——
   与项目既定「读数读的是工作树」同口径：**改了没落盘，判据看不见**。
2. 清单条目里的**人话**（阶段号 / 码表名 / 下界的取值理由）**判据不读** ⇒
   把「M19 是模拟器编译码」那句话写成别的机制，集合照样对得上 ⇒ 本条判据抓不到
   （它抓的是**集合**，不是**说法**）。
3. 空集守卫的下界写作 **20**（当前条数）：将来**删**一条机制时它会先红 —— 那是**期望行为**
   （删机制必须同时改三处），不是缺陷。
4. 本判据**不覆盖**「下界的数值是否仍然合理」—— 那由各族自己的三态闭包判据盯着，
   每条下界旁边写着「为什么取这个数」。
5. ⚠ **本阶段没有把「软件侧」清空**：还开着 **#39** 与 **#45**；
   **#61p / #61q / #61r / #61s / #61k** 属口径 / 产品决定，**#58** 与 §5 属环境限制。
