## 113.5 表的设计：17 探针 / 18 条声明

**探针**（数据面 12 ＋ 输入面 5）：

| 类别 | 分量 |
|---|---|
| 服务侧 | `用户数` / `停用用户数` / `锁住用户数` / `失败次数合计` / `角色数` / `开放管理用户` / `权限位合计` |
| 窗口侧 | `用户列表` / `角色列表` / `审计条数` / `审计面板` / `标题尾` |
| 输入面 | `选中用户名` / `选中角色` / `新用户名长度` / `新密码长度` |

三条设计决定：

1. **权限位要一枚具体的 ＋ 一枚伞**。`开放管理用户`（几个角色能管用户）给 `BtnSaveRole` 一条可读的
   声明值；`权限位合计`（全部角色掩码之和）是**伞** ⇒ 九枚复选框里**任何一枚**真被回写都会抬起来。
   ⚠ 伞必须读**掩码本身**：换成「开着的角色数」这类计数会漏掉「拨掉一位」（值变小）。
2. **`标题尾` 是本宿主唯一的「有反馈」见证**。它没有 `StatusText` 那种提示行 ——
   `ShowStatus` 把提示写进 `Window.Title`（`「窗口名 — 提示」`）。归一化口径与同族的 `StatusOf` 一致
   （`空` / `非空`），**不冻结文案**。没有它，`BtnRefreshLog` 只能写成一条**零信息**的 `Inert`。
3. **审计日志拆两枚**（`审计条数` 服务侧 / `审计面板` 控件侧）—— 合成一枚就分不清
   「服务里没有」与「有但没显示到面板上」（与 `ConnEnabled` 的两档「没有」同一条理由）。

**两处「顺序即语义」**（都不是随手排的，排错会让负控**静默失效**）：

① `BtnRefreshLog` **排第一** —— 只有它看得见「`标题尾` 空 → 非空」这个迁移；排在它后面每条
`ShowStatus` 的按钮看见的都是「非空」，读数上再也分不出「这次点击到底有没有反馈」。
② `PermManageUsers` **紧邻在 `BtnSaveRole` 之前** —— 保存读的是**界面当前状态**
（`GetPermissionsFromUI()`），把这枚拨开是「保存会写新值」的**唯一**来源；中间只要再插一条
带角色布景的声明，`ShowRoleDetail` 就会把 `IsChecked` 刷回模型值。
⚠ 这条依赖是**自证**的：真被刷回去 ⇒ 声明值 `2` 对不上实际 `1` ⇒ 红。

## 113.6 🩸 首跑打脸的两处（「按实测修正声明」）

### 113.6.1 审计那一半：我搜错了地方

开工前我下的结论是「用户管理**一条审计都不落**」，依据是 `RecordAudit(` 全仓只有
`MainWindow` 导出那一站在调。真跑一次读数直接打脸：

| 按钮 | 实测 |
|---|---|
| `BtnAddUser` | `审计条数` 0 → **1**、`审计面板` 0 → **1** |
| `BtnToggleEnabled` | `审计条数` 1 → **2**、`审计面板` 1 → **2** |

根因：审计条目有**两级入口**。公开的 `RecordAudit(...)` 只是给仓外调用方的壳；
`CreateUser` / `DeleteUser` / `SetUserEnabled` / `ChangeUserRole` 走的是**私有** `AppendAudit(...)`
（写同一个 `_auditLog`、同样触发 `AuditLogged`）。
⇒ **量「谁在写」要搜写入点（`_auditLog.Add` / 私有 helper），不是搜公开入口名。**

### 113.6.2 `BtnClearLog` 从 `Inert` 转 `Moves`

上一条事实一改，这一条当场翻档：审计面板到这里是 **2**，清空**真的动了**（2 → 0）。
新声明把两枚分量一起写，正好把源码里那句注释
「审计日志设计为 append-only，这里的『清空』**仅指 UI 显示**」钉成**可证伪**的：
`审计面板` 2 → 0 而 `审计条数` 2 → 2（服务侧一字未动）。

### 113.6.3 顺带量出来的两处「绕过服务层」差分

`OnUnlockUser`（直接写 `_selectedUser.IsLocked`）与 `OnSaveRole`（直接写 `_selectedRole.Permissions`）
**都不落审计** —— 而 `BtnToggleEnabled` 改的同样是用户，却落了 2 条。
`审计条数` 在几条声明里一起读得到这个差分，**双向口径把它变成活的**：
谁给这两处补上服务层调用，那一条就红。

## 113.9 教训与诚实边界

1. 🩸 **「提过名字」会永久豁免一个缺口** —— 残余探针按**名字**去重，
   一个名字只要被任何一层提过一次（哪怕是登记成「静默」），它在残余里就**再也不出现**。
   本次的 8 个按钮就是这样藏了 6 个阶段（阶段 107 起）。⇒ 名字级口径**只能用来排优先级，
   不能用来判「这一层覆盖完了」**。
2. 🩸 **量「谁在写」要搜写入点，不是搜公开入口名**（§113.6.1）。
3. 🩸 **对拍要先剥墙钟，再把「重排」和「真差异」分开**。
   MSBuild 的引用清单与并行测试程序集的结束顺序每次都不同，逐行 diff 会把
   「同一行换了位置」报成一对 `+/-`：本阶段 46 行位移里**只有 2 行是真差异**。
   只看 `+/-` 计数会把「本阶段改了什么」直接埋掉。⇒ `gate-diff.py` 已改成
   **多重集差得真差异 ＋ 位移单列一个数**。
4. ⚠ **`PC1` 这一档（必须保持绿的反证）没有判据兜底**：它证明的是一句对**现有实现**的解释，
   实现一改它就静默失效。要收它得让判据自己去查「处理器体是不是空的」——
   而那是**另一条面**（源码面），本层不做。如实登记为盲区。
5. ⚠ **`Inert` 的 `Why` 仍免证**（阶段 110 §110.5 / 112 §112.8 同一条）：本宿主 10 条 `Inert` 里
   9 条「④ 事件从未订阅」的成色是**手工读代码**得出的，写错没有任何东西会响
   （只有 `NC6` / `PC1` 这一对把「红需要两个条件」钉住了）。
6. ⚠ **本层的面外**：`UserList` / `RoleList` / `AuditLogPanel` 三个 `ListBox` 的**行内控件**
   （`CreateUserListItem` 里 `new` 出的 `TextBlock`）与 `DetailDisplayName` / `DetailRoleCombo`
   两处 `OnDetailChanged` 的目标，都不是按钮 ⇒ 不在本层视野内。

   **`#66`（本阶段新开：8 条已修 ＋ 2 条待决）**。
