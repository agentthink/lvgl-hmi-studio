# 运行时凭据校验：从"登录屏是装饰品"到设备端真校验（2026-09-16）

> 承接 `docs/2026-09-14-optimization-directions.md` 的 **P2-2** 后半、
> 以及 `docs/2026-09-16-permission-model-sinking.md` 末尾登记的遗留：
> 「真实凭据校验仍未做」。本轮把它做完 —— 编辑器配的用户与口令，真正决定设备能否登录。

## 1. 症状：登录屏上填什么都能进

落地前的形态，用户侧看是这样：

| 用户看到 | 实际发生 |
|---|---|
| 登录屏有用户名框 + 密码框（`PasswordMode` → `lv_textarea_set_password_mode`） | 控件是真的，渲染也真的 |
| 登录屏有「登录」按钮 | 按钮动作是 `Login` |
| 按钮按下去 → 进去了 | `hmi_login()` 第一步就是切到登录屏 ⇒ **自己切自己** |

于是两个输入框从来没被读过一次。这条不是"功能没做"的常规形态 ——
它是**功能看起来做了**：UI 齐、按钮齐、点了有效果，唯独凭据不参与任何判断。

## 2. 归因：四个环，环环皆缺

按"数据从哪来 → 怎么下去 → 谁校验 → 谁取值"拆成四环，逐环查现状：

| 环 | 位置 | 现状 | 缺口 |
|---|---|---|---|
| ① 凭据来源 | `AuthenticationService._users` | 进程内 `Dictionary`，不落盘 | 运行时用户表要能进工程并保存 |
| ② 下发 | `SecurityConfigCodeGen` | 只有角色表 | 用户表宏、盐/哈希格式契约、策略宏 |
| ③ 设备端校验 | `hmi_actions.c` | `hmi_login_as_role(user, role_id)` **无密码参数**；固件全树 grep `sha256`/`mbedtls` **零命中** | 哈希实现 + 校验 + 失败锁定 |
| ④ 登录屏取值 | `CodeGenerator.Actions.cs` | `Login` 动作**无参** → `hmi_login()`；生成代码里**从未出现过** `lv_textarea_get_text` | 取值契约 + `Login` 动作拆分 |

不拆环就会得出"补个校验函数就够了"的错误结论 —— 实际是四个环一次都没通过。

### 2.1 一个必须先纠正的前提：编辑器凭据 ≠ 运行时凭据

编辑器自己的 `AuthenticationService` + `UserProfile` + 用户管理界面看起来"凭据存储是现成的"，
**但不能拿来用**，而且不该用：

| | 编辑器凭据 | 运行时凭据 |
|---|---|---|
| 用途 | 谁能打开编辑器 | 谁能操作这台 HMI |
| 存储 | 进程内字典，不落盘 | 随工程落盘，**而且要下发到设备** |
| 复用后果 | 编辑器 admin 口令进了固件 ⇒ 任何拿到固件 dump 的人（SPI NAND 可读、`/rom` squashfs 可解）都能离线爆破出编辑器口令；反过来设备的弱口令也成了编辑器入口 | |

⇒ 立契约：两侧**无数据通路**，只共享**算法**（`RuntimePasswordHasher` 提供哈希实现的语义）。

## 3. 切法：三刀，按数据流依赖排序

| 刀 | 范围 | 验证标准 |
|---|---|---|
| 1 | 运行时用户表进工程 + 下发（①+②） | 序列化往返；生成头出现 `HMI_SEC_USER_COUNT` / `HMI_SEC_USERS_INIT`；**设计模式产物逐字节不变** |
| 2 | 登录屏取值 + `Login` 动作拆分（④） | 生成产物出现 `lv_textarea_get_text`；两种语义分开 |
| 3 | 设备端真校验（③） | 固件 SHA-256 + 固定向量 host 测试 + 失败锁定 |

**顺序不可换，且第 2 刀不能单独合入** —— 生成代码开始提交凭据、而设备端还没有表可查时，
唯一不退化的选择是"密码非空就放行"，那比现状更糟（现状至少一眼看出来没校验）。

## 4. 跨语言算法契约：两侧向外部真值收敛

算法：`h0 = SHA256(salt ‖ utf8(password))`，再迭代到 `HMI_SEC_HASH_ITERATIONS`，
存盘格式 `"Base64Salt:Base64Hash"`。

两个实现，各在一侧：

| 侧 | 实现 | 消费 |
|---|---|---|
| 编辑器 | `Core/Security/RuntimePasswordHasher.cs` | 生成用户表时算哈希 |
| 设备 | `firmware/t113/app/runtime/hmi_crypto.c` | 登录时校验 |

**这里最危险的失效形态是"两侧一起错"**：所有账户都登不上，而两侧的代码各自看起来都对。
所以判据不能是"用 C# 算一遍再断言 C# 算出来的值" —— 那两边一起错也不会红。

⇒ 固定向量取自**独立实现**（Python `hashlib`），两侧共用同一组
（`RuntimeCredentialVectors.cs` ↔ `hmi_crypto_test.c`）：

| 关注点 | 怎么钉 |
|---|---|
| 迭代次数语义 | `iter=1` 必须**等价于单次** `SHA256(salt‖pwd)`（不多跑一轮）；另有 3 轮、1000 轮两档 |
| 盐真的参与运算 | 同口令 + 不同盐 ⇒ 不同摘要（两侧各一条） |
| SHA-256 本体 | 7 条标准向量，覆盖 0/3/43/56/64/65/112 字节（含 padding 跨块与 update 分块边界） |
| Base64 | 12 条（非法字符、`=` 位置、长度非 4 倍数、缓冲区不足一律拒绝） |
| 轮数一致性 | `Verify_RejectsHashProducedWithDifferentIterationCount` 把"两侧轮数必须一致"变成可执行断言 |

**迭代次数刻意不存进格式**：存盘里只有 `salt:hash`，轮数是常量（`HMI_SEC_HASH_ITERATIONS`）。
这样调强度只需改一处常量并重导出，不会出现"表里是旧轮数、代码按新轮数算"。

## 5. 固件端的四条判据

### 5.1 口令长度不足**不计入**失败计数

第一版实现里，`strlen(password) < HMI_SEC_PASSWORD_MIN_LEN` 会调 `hmi_user_register_failure`。
改掉它，理由不是"迁就测试"，而是三条坏处对零收益：

| 理由 | 说明 |
|---|---|
| 探测不到东西 | 攻击者本就知道自己输了几位 |
| 可用性有损 | 操作员手滑少输一位就推进锁定倒计时（5 次锁 15 分钟） |
| 把锁定变成 DoS | 连发短口令即可锁死任意已知账户 |

长度不足的输入**根本没进入密码空间**（连哈希都没跑），等价于"格式非法的输入"，不构成一次猜测。

### 5.2 锁定用单调 tick，不用墙钟

锁定期截止存 `lv_tick_get()` 的毫秒，并以 `0` 作"未锁定"哨兵（常规路径完全不碰 tick）。
墙钟遇 NTP 校时会让"锁 15 分钟"变成锁 3 分钟或锁 40 分钟 —— 项目里有现成的"墙钟回卷"教训。

### 5.3 `hmi_login` 按有无用户表**语义分流**

| 工程配置 | `hmi_login()` 行为 |
|---|---|
| 无用户表（`HMI_SEC_USER_COUNT == 0`） | 切登录屏 + 按**默认角色**授权（既有行为，产物不变） |
| 有用户表 | **只跳屏、不授权** |

第二行是关键：若仍有用户表时自动授权，则"在登录屏上点一下登录按钮"就已经以默认角色进入会话，
凭据校验被**完全绕过** —— 这恰是本功能落地前的状态。

### 5.4 校验通过后仍走唯一接缝

`hmi_login_submit` 成功后调 `hmi_login_as_role(user, role_id)` —— 角色 → 权限的映射
只有一条路（`hmi_role_lookup` + `HMI_SEC_ROLES_INIT`），不允许在凭据路径里另算一遍掩码。

## 6. 模拟器端：**不做**凭据校验，而不是"抄一份"

模拟器的既有注释写着"凭据校验同样未实现" —— 那句话本身就是"预览撒谎"：模拟器里点一下进去了，
烧到设备上进不去。但直接把固件的 `hmi_login_submit` 抄过来**也不是好答案**：

> 它含查表顺序、长度短路、失败锁定、格式严格性等一串判据。重写一遍必然与设备漂移，
> 而漂移的表现是"预览能登、设备登不上" —— 归因成本极高。

⇒ 采用**零运行时重复**的方案：

| 关注点 | 做法 |
|---|---|
| 校验逻辑 | 模拟器**不做**（SHA-256/Base64 只在设备端编译） |
| 预览身份 | 把「用户 → 权限掩码」在**生成期**算好内联进 `main.c` |
| 怎么用 | `--login <用户名>` 以某身份进入会话；**不带该参数就是未登录**（与设备一致） |
| 凭据提交入口 | `hmi_login_submit` 在 `main.c` 里有定义但**一律拒绝**并说清原因（不静默放行、不假装校验过） |
| 刻意差异 | 模拟器不做失败锁定（安全加固，不是预览对象）—— 写在生成代码注释里 |

掩码的单一来源是 `SecurityConfigCodeGen.BuiltInRoles` + `MaskHex` ——
角色表清单与掩码计算**只有一份**，否则「生成头的角色掩码」与「模拟器预览掩码」会静默不一致，
那正是"预览能点、设备点不动"。

### 6.1 顺带补上的一条链接契约

生成的 `generated_hmi.c` 现在会引用 `hmi_login_submit`。它的宿主声明加在
`CodeGenerator.Simulator.cs` 的宿主 API 块里，于是
`SimulatorLinkContractTests` 的**穷举守卫**（从生成代码反推它要求宿主提供什么）自动把它纳入 ——
漏给模拟器补定义会在单元测试阶段变红，而不是等到 `cmake` 链接期。

## 7. 诚实定位：这套东西防的是误操作，不是攻击

把话说清楚，免得后人高估它：

| 挡得住 | 挡不住 |
|---|---|
| 操作员误入受限界面后随手点进来 | 拿到固件的人离线爆破 —— 单轮 SHA-256 结构 + 迭代 1000 次，弱口令仍是秒级/分钟级 |
| 用错账号（角色不对 ⇒ 门不放行） | 物理接触设备后重刷固件 |
| 连错口令（5 次锁 15 分钟） | 用短口令探测（本来就探测不到东西） |

要抗离线爆破需要 PBKDF2 / Argon2 级 KDF，设备端引入那套实现是另一个量级的工程量。
而车间 HMI 的主威胁模型是"操作员越权改配方"，不是"攻击者物理接触设备" —— 所以本轮**刻意不做**。
