# 临时产物的生命周期：`TempRoot` 会话层

> 承接 `docs/2026-09-15-app-paths-single-source.md`（第十轮 `541813d`：路径**来源**收口）。
> 第十轮解决了"写到哪儿"，这一轮解决"**写完谁清**" —— 两半合起来才是完整的生命周期。

## 1. 归因

**一句话**：临时产物的生命周期从来没有被建模 —— `TempRoot` 下混着两类语义完全不同的东西，
而清理策略只能有一个，于是无论怎么定都是错的：清掉就破坏增量复用，不清就涨到占满磁盘。

第十轮已经识别出"16 处各写各的路径"。本轮识别出的是**另一半**：那 16 处里有一半产出的东西
**没有任何释放点**。

| 类别 | 例子 | 语义 | 现状 |
|---|---|---|---|
| 跨会话复用 | `so-build` / `compile` / `download` / `sim/<name>` | 稳定名，下次运行还要用（增量编译复用） | 数量有界，**不能**一刀切清 |
| 会话级 | 工程解包目录、资产工作目录、部署中转文件 | 本次运行专用，进程退出即无主 | **没有任何释放点** ⇒ 无界增长 |

### 1.1 第十轮把它从"会被清的地方"搬到了"永不被清的地方"

这是本轮最关键的判断。第十轮把两类东西一起从 `Path.GetTempPath()` 搬到了
`%APPDATA%/zhishu-hmi/temp`：

- 对**跨会话复用**类，是**改进** —— 不再重启即失，增量复用时不用重建。
- 对**会话级**类，是**退化** —— `/tmp` 至少在重启/系统清理时会空掉，
  持久根**永远不会**。

**上一轮修掉了一个兜底，同时撤掉了另一个兜底。** 这不是第十轮做错了（搬是对的，
`/tmp` 只有 10 MB 且共享），而是搬家的同时**必须**把生命周期补上。

### 1.2 活证据（本轮实测，不是推理）

```
~/.config/zhishu-hmi/temp/          ← 真实数据根
  so-build-0541a419…/   so-build-5d76c61f…/     ← 唯一名，无主
  written-5012913a…/    written-e8c63b9c…/

<repo>/.hmi-test-tmp/appdata/temp/  ← 测试进程的重定向根
  so-build-<guid>   × 20
  written-<guid>    × 15
  comm-config-<guid>.ini × 6
```

后一组是**测试自己跑出来的**：`AppPathsTests` 每跑一次全量就多两个 `so-build-<guid>`、
一个 `written-<guid>` —— 测试套件在稳定复现同一个缺陷。顺手修掉了（见 §5）。

### 1.3 放大面

`MainWindow.CreateWorkspaceDirectory` 有 **4 个调用点**：

```
OpenHmiFile  .json 分支        → 1 个（资产目录）
OpenHmiFile  .hmi  分支        → 2 个（解包临时目录 + 资产目录）
NewProjectCore                 → 1 个（资产目录）
```

也就是说 **打开一个 `.hmi` 工程就建 2 个唯一目录**，里面是解包后的工程内容与用户导入资产的
**完整副本**。

### 1.4 第二层缺口：唯一名 ≠ 有主名

`NewTempSubdir` 原来的注释写着「用于**每次调用独立**的工作目录 —— 并发调用（多实例、并行测试）
不会互相踩」。意图是对的，但**唯一性只解决了「不互相踩」，没解决「谁负责删」**。
`hmi-editor/<name>-<guid>` 这种形态在命名上就已经放弃了可追溯性。

## 2. 设计：会话层

```
TempRoot/
  <稳定名>/                    ← 跨会话复用：so-build / compile / download / sim/<name>
                                  稳定名，**不自动清理**（增量复用依赖它）
  .sessions/<pid>-<token>/     ← 会话级：NewTempSubdir / NewTempFilePath 的产物
                                  有主，整体释放
```

**释放途径两条**：

| 时机 | 做什么 | 覆盖 |
|---|---|---|
| 进程**正常退出** | `ReleaseSessionTemp()` 删掉自己的会话目录 | 常规路径，精确 |
| 应用**启动** | `PruneStaleSessions()` 扫掉不属于存活进程的会话目录 | 崩溃 / 强杀留下的孤儿 |

API 形状（调用点**零改动** —— 只有 `NewTempSubdir` / `NewTempFilePath` 的内部实现变了）：

```csharp
SessionTempRoot                 // TempRoot/.sessions/<pid>-<token>，不建目录
NewTempSubdir(prefix)           // → 会话目录下，唯一名
NewTempFilePath(prefix, ext)    // → 会话目录下，唯一名，不建文件
ReleaseSessionTemp()            // 删本会话目录并重置会话 id，返 bool
PruneStaleSessions(isAlive?)    // 返回删除数；探针可注入
```

### 2.1 为什么 pid 编码在目录名上，而不是给目录写 owner 标记文件

两种做法都能实现"判断这个目录还有主吗"，但**失败模式的方向相反**：

| 方案 | 失败时的表现 | 后果 |
|---|---|---|
| **pid 在目录名里**（采用） | 名字解析不出 pid ⇒ 跳过 | **漏删**（浪费空间） |
| 目录内写 owner 标记 | 标记写失败 / 被删 ⇒ 看起来无主 | **误删**（另一个实例正在用） |

代价不对称：漏删只是浪费空间，误删会让另一个正在运行的实例当场失败、或删掉用户正在用的文件。
所以判据一律偏保守。pid 复用的后果同样是**漏删**（把别人的目录当活的留着），可接受。

### 2.2 会话 id 缓存的是 id，不是路径

`DataRoot` 有意不缓存（环境变量中途改要立刻生效，见第十轮）。会话来不得缓存**完整路径** ——
否则"先访问、后改环境变量"会让会话目录留在旧的临时根下，出现"半新半旧"的状态，
比全旧更难排查。所以缓存 `<pid>-<token>` 这一段，路径每次从当前 `TempRoot` 现算。

缓存 id 本身是必要的：它是**进程身份**，在进程生命周期内不该变；
不缓存的话，同一进程的产物会散进多个会话目录，整体释放就漏了。

## 3. 清理判据（五个方向，全部偏保守）

| 情形 | 判据 | 结果 |
|---|---|---|
| 名字就是本进程当前的会话 id | 正在用 | **不删** |
| 名字解析不出 pid（`not-a-session` / `12345` / `0-x`） | 不是本机制创建的形态 | **不删** |
| 同 pid、不同 token | pid 已被本进程复用 ⇒ 那个 pid 的**前任**必死 | **删** |
| 探针判死 | 无主 | **删** |
| 探针抛异常（权限 / 平台限制） | 判不出来 ⇒ 当作存活 | **不删** |

第三条是唯一能"确定同号已死"的情形，也是最容易被漏掉的一条：那个 pid 现在**活着**，
活的就是我们自己 —— 单靠存活判定永远发现不了这种残留。

**扫描面只有 `.sessions/`**，稳定名工作目录不在面内 —— 增量编译复用不受影响。

## 4. 接线

| 时机 | 调用 | 位置 |
|---|---|---|
| 应用启动 | `AppPaths.PruneStaleSessions()` | `App.OnFrameworkInitializationCompleted`，`Task.Run` 后台跑（纯 IO，不该拖慢启动；失败不阻断） |
| 应用退出 | `AppPaths.ReleaseSessionTemp()` | `MainWindow.CleanupOnShutdown`（与 Timer / Modbus 驱动一起释放） |

### 6.1 两次翻车（都值得记住）

**① harness 解析没对上，6 组全被读成"全绿"。**
带 `--filter` 时控制台 logger 的失败标记是 `[FAIL]` **后缀**形式、汇总是 `失败数: N`，
而我按 `失败 <名字>` 前缀 / `失败: N` 解析 ⇒ 零匹配 ⇒ 输出与"注入完全无效"一模一样。
差点据此得出"这些判据没有任何测试守住"的错误结论。**又一次「全绿先问比到了吗」** ——
去翻日志才看到 `[FAIL]` 行和 `构建 … -> HmiEditor.Core.dll` 都在，说明注入生效、只是没解析出来。

**② 基线被自己的测试污染变红。**
`NewTempSubdir_DoesNotAccumulateUnderTempRoot` 断言"临时根直下不得有 `leak-probe*`" ——
这是**绝对空**，而临时根是跨次运行共享的：上一次注入实验留下的 5 个同名目录让它永久变红。
判据只该依赖**本次运行的增量**。改用隔离根后既自洽、判别力不变。

## 9. 历史平铺残留：按形态清理（2026-09-16 收尾）

### 9.1 残留长什么样

本机实测 `~/.config/zhishu-hmi/temp/` 直下（时间戳落在 2026-09-15 22:39–22:43）：

| 名字 | 内容 |
|---|---|
| `so-build` | **现行稳定名工作目录** —— 要留 |
| `so-build-<32hex>` × 4 | 空 |
| `written-<32hex>` × 2 | 各含一个空 `sub/` |

它们来自第十轮～第十一轮之间的实现：那时 `NewTempSubdir` 的产物**直接落在 `TempRoot` 直下**。
第十一轮把唯一名产物收进 `.sessions/` 之后，这个形态**现任代码已不可能产生**——
稳定名产物（`so-build` / `compile` / `download` / `sim`）**不带** guid 后缀，
唯一名产物一律在 `.sessions/` 之下。所以「直下 + guid 后缀」只剩历史残留一种解释。

### 9.2 判据：按**名字形态**清，不按"时间点"

```
TempRoot 直下 且 名字形如 <非空前缀>-<32 位小写十六进制> 且 最后写入早于本进程启动  ⇒ 删
```

三个保守点，每个都对应一种具体的误删：

| 判据 | 挡住的误删 |
|---|---|
| 只扫**直下**（不递归） | 递归会扫进 `.sessions/`，而现行会话目录名**正好也是** `<pid>-<32hex>` —— 整层被端掉 |
| 后缀**恰好 32 位小写十六进制** | 差一位、大写、含 `g` 都不认。判据越贴近"只有旧实现能造出来"，误删面越小 |
| 最后写入**早于本进程启动** | 另一个还在运行的实例（旧版本）刚建的工作目录可能正被使用 |

### 9.3 为什么是"幂等"而不是"打标记只做一次"

一次性迁移要记录"做过了"：标记写失败 ⇒ 永不重试；标记丢失 ⇒ 重复执行。
按形态清理是**幂等**的 —— 没残留时只是一次目录枚举，有残留时自动删，删到一半崩了下次继续。
代价是判据必须严格到「现任代码绝不产生它」，**所以 9.2 的第二个保守点不是可选项**。

### 9.4 真机验证（用产品侧同一段代码）

没有另写一份清理判据 —— 否则"手工清理"与"应用启动自动清理"会各有一套标准，迟早分叉。
做法是 `dotnet run` 一个 file-based 单文件（`#:project` 引 `HmiEditor.Core`）直接调

```

  so-build
```

`so-build` 保留 —— 这条同时证明了「不误伤稳定名工作目录」在**真实根**上成立，而不只是在隔离根里。
