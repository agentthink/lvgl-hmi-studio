## 118.2 🩸 推翻登记表里的一句话：按「个数最多」挑下一刀是错的

**「最大」成立，「最该扩」推不出来。** 我一开始确实是按「面外哪一格数字最大」挑的，
摸面摸到一半发现自己站不住，回头读了三条实测：

|---|---|---|
| ① | 它的**数据面已经被判过** | `PropertyPanelWiringTests` 从**逻辑树**枚举全部 **70** 个编辑器、按 **26 个控件类型场景 ＋ 1 个屏幕场景**逐个驱动，断言 `uncovered == 0`（9 个驱动不动的带理由豁免 ＋ 一条 `ExemptionList_HasNoStaleEntries` 反陈腐检查）。本层扩它主要是**重复记账** |

🩸 **这一条比「加了第 9 个宿主」更重要**：**账本的覆盖范围自己没被钉住**，
就会把「个数最多」误当成「优先级最高」。这是「面的边界 ≠ 没有缺口」的又一形态 ——
**账本的排序口径 ≠ 覆盖缺口的大小**。

Probe 8 枚：`列表条数` / `引擎条数` / `活动数` / `已确认数` / `已恢复数` / `空提示` / `选中下标`（输入面）/ `状态文案`。

🩸 **两个刻意的细节**：

1. **`选中下标 → -1` 不是凑数**：`RefreshData()` 走 `AlarmList.Items.Clear()` 重建整列 ⇒
   选中被丢掉（用户确认一条之后，要重新点一次才能确认下一条）。本层这是该行为的**唯一**见证。
2. **造数顺序是判据的一部分**（写进 `SeedAlarmRecords` 的 xmldoc）：列表按 `OccurredAt`
   **降序** ⇒ **最后造的那条排最前**；而 `BtnAcknowledge` 只确认**选中项**、`AcknowledgeAlarm`
   只对 `State == Active` 返回 `true` ⇒ 必须让一条 `Active` 落到 `index 0`，
   否则确认会**静默失败**、那条声明变成 flaky。
3. **不能 `Sleep`，必须轮询**：`UpdateVariableValues` 只写字典、**不触发评估**；
   记录由**定时器**造（`EvaluationIntervalMs` 默认 500 ms，可设到最低 50 ms）⇒
   本轮本地写了 `WaitUntil`（**超时即抛**，不把「没等到」静默变成「读数恰好如此」）。
   ⚠ 沙箱里 `TestWait` 跨项目不可用（它只在 `tests/HmiEditor.Core.Tests/Support/`）。
