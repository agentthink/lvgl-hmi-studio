## 2. 挑宿主的五条判据

1. **可读的数据面** —— 处理器写的东西里有能被探针读到的分量（模型字段最好；界面文案要走字典 ⇒ 只能读"空/非空"）。
2. **零驱动** —— 它的控件在既有测试里 `grep` 零命中（⚠ "构造 → Show → 布局"那一层不算驱动）。
3. **写入面** —— 若处理器**每次事件把全部编辑器写回模型**（批量写），与本层核心断言
   "未声明的分量一字不变"**正面冲突** ⇒ 不扩（`PropertyPanelView` 就是这么被否的）。
4. **可达** —— 生产里真会被构造（`new`/XAML 标签）；阶段 135 的 `UnreachableViewGuardTests` 会兜底。
5. **代价最小** —— 面内控件数少、且**接线形态简单**（按钮族 < 选择族 < 树路径 < 指针序列）。

## 3. 建夹具（`WindowDepot`）

- 每个宿主拿一个**全新的** `WindowDepot`；需要额外状态时**写一个 `SeedXxxFixture(depot)`**，
  在本宿主的 `Build` 里调 —— 别去改 `WindowDepot` 本身（那会影响别的宿主与 `WindowProductionPathUiTests`）。
- **必须让"前置"在夹具里成立**，否则腿会退化成"提前 return"的零信息断言。例：
  * 列表要 ≥2 行（`SeedAssetFixture` / `SeedPickerVariables`）；
  * **引擎要真的解析得到变量**（阶段 142 实测：`RuntimeBindingEngine` 走 `_project.VariableManager`，
    变量挂在 `depot.Variables` 上它会**静默不建标签** ⇒ 标签数恒 0）；
  * **命中矩形不能是 0×0**（阶段 144 实测：控件不写 `Width/Height` ⇒ 指针永远点不中）。
- 🩸 **不要把夹具换成"另一块屏"**（阶段 146 实测）：画布/面板会把屏幕**适配进自己的视口**
  ⇒ **换屏等于换坐标系**，原先算好的指针坐标全部失效。要改计数就从**现有屏**上想办法（例：按 `2 → 3` 判）。
- 🩸 **宿主自己就是 `Window` 时，先查有没有 `Parent == null` 这类"已装配"守卫**（阶段 157 实测）：
  `UserControl` 宿主可以靠「装进 `Window.Content`」把 `Parent` 装配出来，`Window` 宿主**不行**
  ⇒ 那些腿只能记 `Inert（前提不满足）`。做法：**加一枚前提分量**（如 `有Parent`）把前提量出来写进读数，
  别只在注释里断言；再配一支"拆前提"负控证明那条 `Inert` 承重。
  ⚠ **但要顺手问一句"这个守卫在产品里成立吗"**（阶段 191/192 实测）：`ScriptEditorView` 的那三个
  处理器在生产形状（`ShowDialog(owner)`：`Owner` 有、`Parent` 仍 null）下**同样**首行返回 ⇒
  那是**真缺陷**（打字不落模型，登记 `#89`），不是夹具限制。阶段 192 修掉守卫后，那两条腿从
  `Inert` 转 `Moves`（**期望值一个字没改**），`有Parent` 分量降级成纯读数。
  ⇒ 记 `Inert（前提不满足）` 时必须写清**前提是"夹具装不出"还是"产品也没有"**，后者要开登记项。
- 夹具里**不要**调用`Refresh*`之类"把效果提前做掉"的方法 —— 那是把效果搬进布景，本层就瞎了。

## 4. 建表：探针与声明

**探针**：`Num` / `Str`（数据面）、`InputNum` / `InputStr`（输入面，只有它允许被布景改）、
`Voice` / `EventObserved(…, isVoice: true)`（只进读数、不进断言）、`EventObserved`（进断言）。

**桶**：`Moves`（声明"变了什么"）、`Inert`（声明"本状态下什么都没变"，**理由必须写清是哪一种成色**）、
`Never`（不点：关窗 / 模态 / `DispatcherTimer` / 异步平台桩）。

**`Inert` 的三种成色（必须点名）**：① 未被观测（有行为但本层没有对应分量）；
② 提前 `return`（前置不满足）；③ 写入同值（值本来就等于要写的值）。**三者都不是"没接线"。**

**顺序有语义**：`SelMoves` 的前提（先选中才编辑）、`Moves` 造出的前提（先加关键帧才有关键帧可选中）
都要在表里按顺序排，并在 `Why` 里写明"顺序不是装饰"。

**唯一性键**是 `(名字, 手势种类与取值)` —— 同一控件可以被驱动**多次**（同名不同下标 / 不同指针路径）。
⚠ 指针腿（`Drags`）加进来之后键是四元组（阶段 145 实测：点一下与拖一段撞键）。

**断言要"读数据"**：优先读**模型**（`TagMonitorView` 的引擎值、画布的 `目标控件X`），
其次读界面里由处理器写的格；**别读本地化文案**（那等于冻一份词典）。

## 5. 卫生：宿主跑前两件事（`#72` 的两半）

```csharp
var silenced = StaticBusHygiene.Silence();          // 阶段 134：清**订阅**（打到已关闭窗口）
var sharedDataReset = StaticBusHygiene.ResetSharedData();   // 阶段 139：清**共享数据**（8 个静态属性）
```

- 两个类都挂在独占集合 `Language-global` ⇒ 清的时候没有别的集合在跑（这是安全性的机制，不是运气）。
- 🩸 **清完之后，产品里"经静态总线推给视图"的那些路就断了** —— 布景/驱动要走**视图自己的属性**
  （阶段 146 实测：`view.Canvas.DrawTool = …`，而不是 `DockLayoutState.SetDrawTool(…)`）。
- 新加一个静态字段/事件时：`ResetSharedData` **没分类就抛**、`Silence` 按类型自动收 —— 别在表外塞东西。

## 6. 负控清单（每个宿主至少这些）

| 类型 | 注入 | 期望 |
|---|---|---|
| 摘接线 | 删掉那条 `+=` / XAML 属性 | 红「声明的分量一个都没动」 |
| 接错处理器 | 把 `Click` 接到相邻处理器 | 红「分量 期望 X、实际 Y」 |
| 声明写反 | 期望值改成另一个值 | 红「期望 X、实际 Y」 |
| 面守卫 | 删掉**全部**该控件的声明（⚠ 只删一条**不红**：`declaredNames` 里还有那个名字） | 静态守卫红、运行期绿 |
| 产品修复类 | 把修复撤掉 / 写入改成常量 | 红在**那条**腿上（证明修复承重） |
| 原语类 | 把新原语的某个执行步变空转 | 红在那条腿上（证明原语承重） |

⚠ **负控的过滤器必须覆盖"可能抓到它的那条腿"** —— 拿不准就跑**全量**（30 s 很便宜）。
🩸 阶段 140 实测：漏了一个类 ⇒ 把一条**已存在**的守卫误读成"盲区"，差点白写一条重复守卫。

🩸🩸 **注入之后、读任何读数之前，先量「被注入那棵树」的形状**（阶段 156 为 `#78` 补）：
负控脚本的定位一旦写错，删掉的可能是**一整段**而不是那一条 —— 于是你量到的"异常"是**注入造成的**，
不是产品/框架的现象。四条便宜的核对，**任一不符就是注入错了**：
① `Hosts.Length`（或等价的"面宽"）还是注入前那个数吗；
② 跑完的**用例总数** = 注入前 ± 预期条数吗；
③ 失败文本点名的**对象**是不是你注入的那一个；
④ **栈帧行号**与 HEAD 对得上吗（差几百行 ⇒ 文件被削掉了一整段）。
⚠ **`--no-build` 让这四条更危险**：编译失败时它照跑旧 DLL，读数看着像"红/绿"、其实是**上一棵树**的。

## 7. 收口工作流

1. 单宿主过滤跑 → 2. 全量跑 **2 次**（顺序/共享状态敏感）→
3. 负控（备份还原 + SHA256 核对 ＋ **注入后先量形状**：`Hosts.Length` / 用例总数 / 点名对象 / 栈帧行号）→
4. `sh scripts/gate-run.sh .workbuddy/tmp/sNNN-gate1.log` → 5. `python3 scripts/gate-readings.py` →
6. 登记表新 §（做了什么/为什么/负控/读数）＋ `project-status.md` 新阶段节 → 7. 提交（`test(sNNN)` ＋ `docs(sNNN)`）。
